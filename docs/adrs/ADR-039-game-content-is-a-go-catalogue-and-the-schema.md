---

A game's content — the stats and their rates and bounds, the actions, the skins, the locations, the labels — lives in one Go file inside that game's package (`content.go`) and is served whole to the SPA by that game's `GET /config`. The database stores **keys as `text`**, never Postgres enums, and holds none of the meaning. The SPA hardcodes no key, no label and no threshold: it renders whatever the config describes.

_Reasoning:_ this is a decision about the cost of a whole class of change, and migrations here are **immutable**, so getting it wrong is permanent. With enums, every new stat, skin, location or object kind is an `ALTER TYPE` — a migration, forever, for a value whose entire meaning is a label and a number. With a column per stat, every new stat is an `ALTER TABLE`. With the catalogue plus `text` keys, adding one is a Go-file edit: no migration, no client deploy, and the value's rate, bounds, label and rendering are all defined in the single place that can validate them against content anyway. A row whose key has left the catalogue is unrenderable and is skipped on read, which is the correct failure for a value only content can define.

_The homogeneous half gets rows; the heterogeneous half gets columns._ A pet's stats are all the same shape — a scalar with a rate and an `as_of` — so they are rows in a tall table, one decay expression covers every one of them, and adding a stat needs no schema at all. A **stat whose rate is zero is a lifetime counter**, which is how this game gets its records without a second runs table. World objects are the opposite: heterogeneous rows carrying contended invariants (`claimed_by`, `remaining`, `exhausted_at`) that must be indexable, `NOT NULL`-able and `CHECK`-able, because a typo silently reading as NULL is the one bug class a contested claim can least afford. Choosing differently in the two tables is the decision, not an inconsistency.

_There is one JSONB body in the schema, and it is this record's own trigger firing rather than an exception to it._ The rule as written held that no JSONB be added speculatively: both candidate uses at the time were cosmetic and derive better from `hash(id)` against the catalogue — zero storage, unable to drift out of step with the content — and an unused escape hatch is where load-bearing state goes to hide from constraints. The trigger to revisit was named with it: *the first kind that needs a persisted, kind-specific, non-derivable value earns either that column or a narrow side table **then**, decided with the concrete case in hand.* The concrete case arrived on 2026-08-04 and is `game_fintech_layouts.body` ([ADR-061](./ADR-061-the-office-floor-is-validated-data-not-a.md)): «СИМУЛЯТОР ФИНТЕХА»'s office floor, which somebody can now **draw by hand**, and which therefore has nothing behind it to derive from — no seed reproduces a floor that was dragged into shape, which is exactly the property the sibling game's eight-byte seed depends on ([ADR-050](./ADR-050-the-level-is-generated-on-the-server-and-sent.md)).

_What the body bought, and why a row per solid was the wrong shape._ The layout is read whole, written whole, and never queried by its parts. A row set would have added an **ordering column** to be maintained forever, because the order of the solids is part of the collision contract with the browser's own copy of the resolver — the push-out runs once per rectangle in layout order, on both ends, and the same rectangles in a different order are a different office to anybody standing between two of them. One opaque value preserves that for nothing, and is the same value that is served.

_And what did NOT move, which is the larger half._ Game **content** is still a Go catalogue: the stats, the actions, the skins, the personas, the phrase pools, the walls and the tuning constants are all still Go, still served by `GET /config`, and still add nothing to the schema. Every `*_key` column is still `text` and there are still **no Postgres enums** anywhere. What is in the jsonb is not a rule but an authored **instance** of one — geometry, held to a predicate in Go before it is allowed to be installed — so nothing about the schema learned a game-specific shape, and nothing about a floor's validity lives in DDL. The distinction to hold on to is *rule versus instance*: a rule goes in the catalogue and is code, an instance may be a row, and a row that starts encoding rules is this record failing rather than flexing.

_Consequence — the client is told what it can DO, never what a thing IS._ The rule above says the SPA holds no content key. The corollary, learned twice while building «Ванягоччи», is what to publish *instead* when the browser genuinely has to act on content: publish the **capability**, and keep the **reason** server-side. The beer store rides the roster as a **structure** — a place and a count — rather than as a kind key, so the client can grey a button by measuring its own distance to a point without ever being able to pick the crate out of the yard. A verb that must be walked to carries `needs_near`, and a verb that is a *search* carries `needs_spot`, and both are read **for their presence and never for their value** — the browser asks "does this verb need a place?", never "is this verb `drink`?". `needs_spot` is itself *derived* on the way out from the kind being hidden, so the rule has one expression and the fact it rests on (**which** kinds are hidden) never leaves the process — publishing that would publish where the key is. The same instinct decides `here`, which is counted by the server and sent rather than derived, because deriving it would mean teaching the browser to tell a person from an NPC.

The test of a new field is therefore not "is this a content key" but "**could the client act on this without learning what any of it means**". A capability passes; a kind key does not.

_Consequence:_ the property is testable rather than aspirational, and is tested — the stubbed Playwright suite serves a config containing a stat and an action the SPA has never heard of and asserts both render, labelled from the config. A client that had learned a content key fails that test. The same rule is why an invariant that must live in the database cannot name a content value in DDL: the "at most one active event of a kind" index is predicated on a `singleton` boolean the catalogue sets at insert time, not on `kind IN ('key', 'beer_crate')`, which would have put content into an immutable migration.
