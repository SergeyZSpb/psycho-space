---

«Ванягоччи» draws its shared world in **ordinary DOM, positioned by CSS**. There is no PixiJS, no Phaser, no `<canvas>` and no render loop. An entity is a `<div>` whose `--x`/`--y`/`--band`/`--depth` custom properties are written imperatively when a frame arrives; the stylesheet maps those to pixels with `container-type: size` and `cqw`/`cqh`, so the 0..1 coordinates on the wire become positions **entirely in CSS** and there is no measured box cached in JavaScript to invalidate when mobile chrome slides. Depth is four discrete bands driving a `scale()` and a `z-index`. A character is an `<img>` with `object-fit: contain` and `object-position: bottom`. Confetti is fourteen absolutely-positioned spans and one `@keyframes`.

_Reasoning, as originally argued._ Three things decided it before the plane existed. **Zero dependency bytes** — a WebGL engine core is in the same order as this entire application's JavaScript, for an audience holding phones on mobile data. **An engine fights the never-scroll layout**, which is the constraint that has already burned this project once: an engine's scale manager keys off `window.innerWidth/innerHeight`, which is exactly what lies on mobile as browser chrome slides, and the existing fix is CSS the browser reapplies for free. And **the crossover was not close** — the estimate was 10 to 20 animated nodes against a DOM/canvas crossover of roughly fifty independently-animated entities, per-frame physics, a camera over a world larger than the viewport, or atlas-driven frame animation at 60 fps.

_Re-examined on 2026-07-27, with the yard actually built, and re-affirmed._ By then the plane had cut-out figures on drawn backdrops, a four-band depth ramp, uploaded sprite art, a confetti burst, a death screen and a control surface — which is the point at which the question deserves asking honestly rather than defending the original answer. The answer did not move, but three of the reasons did, and they are stronger than the ones above.

**Nothing that was hard about building it was the renderer.** A full day's work on the yard was made difficult by exactly three things: an absolutely-positioned box at `left: 50%` shrink-to-fitting against *half* its parent, so a speech balloon wrapped at thirty pixels whatever its own cap said; `overflow-wrap: anywhere` splitting a Russian word across two lines, which reads worse than the ellipsis it replaced; and migrating about thirty end-to-end tests off a control row that had moved. An engine removes the first two footguns and supplies its own, and makes the third dramatically worse.

**The test surface is now the strongest argument, and it did not exist when the decision was first made.** Several hundred assertions describe this plane: depth ordering resolved through `document.elementFromPoint` because a computed `z-index` proves nothing about stacking, a figure's feet staying on the ground through every pose, a badge's overhang as a fraction of its box, label and balloon caps at 320 px, tap targets at 44 px, and `prefers-reduced-motion` genuinely reaching the yard rather than being silently out-specified. Every one of those is possible *because the yard is DOM*. On a canvas they become pixel comparisons or a test-only introspection API — and shipping a test hook into a production path is forbidden here, so it would be pixel comparisons, which are the tests that rot and get deleted. This bears directly on [ADR-021](./ADR-021-two-playwright-suites-on-purpose.md): both Playwright suites are built to assert on real layout, and a canvas would blind both of them at once.

**Several things that are free in the DOM would be bespoke work in an engine.** Reduced motion cost one CSS block. Text — speech balloons, names, the death screen, the readout — is real text, with real accessibility, wrapping in a language whose words are long. `object-fit: contain` plus `object-position: bottom` *is* the entire cut-out renderer. In an engine each of those is anchor maths, a texture loader, a text renderer and a reduced-motion story written by hand.

**And the constraint this game actually has is bytes on the wire, not draw calls.** Every design argument that has bitten since launch has been about the socket rather than the screen: the avatar demoted from the frame to a badge fetched by id, because a couple of hundred unchanging characters at 5 Hz is about a megabit a second at ten players ([ADR-037](./ADR-037-one-account-is-one-entity-and-the-wire.md)); `loc` omitted for the default location; the beer store published once as a shared block rather than as a field on every entity. An engine does nothing whatsoever about any of that, and its bundle makes the thing that *is* the constraint worse. Sparse networked updates also strengthen the DOM case rather than weakening it: frames arrive at 5 Hz and the render path interpolates between them with CSS transitions, which is *less* per-frame work than the locally-simulated animation engine renderers exist to win at.

_What it costs, stated rather than waved away._ CSS has its own sharp edges and this record should not pretend otherwise: specificity silently deciding whether a media query applies, shrink-to-fit rules that are not obvious, `boundingBox()` reporting layout rather than paint so a test can mis-read a clip, and a stylesheet that must be re-reasoned about whenever the world scale moves. Those are real and they have all cost time. They are accepted because they are *inspectable* — every one of them was found by a test asserting on a real box, which is precisely the property a canvas would remove.

_What would change this decision._ Written as triggers rather than as a feeling, so that a future reader can check them rather than re-argue the whole thing:

- **Frame-by-frame sprite animation** — walk cycles, idle loops. CSS `steps()` over a sprite sheet handles this, so it probably still does not flip it; it is the first thing that makes the question worth re-asking.
- **A world larger than the viewport** — a camera, scrolling, culling. Today the plane is a fixed 3:4 box and that is a *rule of the game* rather than a layout choice, because walking speed is defined in plane-widths per second and only means the same thing to two players if a plane-width does. This would be a redesign of the world before it was a rendering decision.
- **Entity counts in the hundreds**, or smooth 60 Hz motion instead of 5 Hz frames plus CSS transitions.
- **`web/src/lib/vanyagotchiPlane.ts` growing a scene graph.** It is about 1400 lines and is already a small engine — depth bands, the position writer, the errand machinery. If it starts sprouting a tween system, a collision layer or a camera, the project is writing an engine badly instead of importing one well.

If it is ever genuinely needed, the runner-up is a hand-rolled `<canvas>` leaf component inside one part of the screen — added for a single effect CSS cannot carry, with the DOM still authoritative for layout, state and every interactive element. A whole-plane engine is the last resort rather than the first, and **PixiJS** rather than Phaser, for the bundle and for the absence of a scale manager fighting the layout.
