A game's roster contains **one entity per account**, not one per connection. The id it publishes is a **pseudonym derived per process** — `HMAC-SHA256(processKey, accountID)`, base64url, truncated — where `processKey` is 32 bytes of `crypto/rand` minted when the service is constructed and never persisted or configured. `Hub.PublishTo(ctx, connID, msg)` is a third game-agnostic seam so a service can answer one connection; a game learns which entity a client is by sending a hello and being told, over that unicast.

The roster also lets a player be **recognised by face** — and it does so **without putting anything about the face on the frame**. The avatar is read from `accounts.avatar_url_enc` through a narrow `Profiles` seam when a client says hello, cached in memory beside the rest of what the plane draws, and served over ordinary HTTP at `GET /api/game-vanyagotchi/avatar/{peer}`, keyed on the same pseudonym. The roster carries no URL, no name and no flag: a client asks for the picture of every entity it draws, using the id it already has, and a 404 — the ordinary answer for every NPC — is what tells it to draw the catalogue art instead.

_Reasoning:_ the identity half and the face half were decided separately, and the second one costs something the first was designed to avoid.

**Signing in on a second device produced a second Ваня.** The hub allows three connections per account, and the roster was keyed by connection, so a phone and a laptop were two dots that could stand in different places and be moved independently. That is a bug about *identity*, not about presence: the hub is right that presence is per connection, and the game is what decides an account is one thing in its world. Keying the game's own state by account fixes it where the decision belongs and leaves `realtime` unchanged.

**The obvious id to use instead was the account's, and it must not be.** `accounts.id` is a durable cross-session identifier, and a roster is broadcast to everybody else in the room — so publishing it would hand every player a stable handle on every other player, permanently, for the sake of drawing a circle. The pseudonym is stable exactly as long as it needs to be (one process) and no longer, which is the same lifetime presence already has: the key dies with the process that minted it, so nothing correlates across a restart. It needs no configuration, and there is no key to rotate wrongly.

**A client cannot recognise itself from a pseudonym**, by construction — that is what makes it one. So the server has to say, and saying it to one connection rather than to the room is what `PublishTo` is for. The request arrives through the existing inbound `Handler`, so no join/leave lifecycle hook was needed and ADR-033's seam count grew by exactly one.

**The avatar is personal data, and showing it to the room is fine; putting it on the frame was not.** Three things settled the first half. The **consent already names it** — «включая отображение имени, фамилии и аватара другим пользователям Приложения» is the declared purpose the user agreed to, so showing a face to another player is the disclosure they consented to rather than a new one, and the stored data set does not change, so no `CONSENT_VERSION` bump and no re-filing follows. It is **already published to the same audience** by the wishlist, by comments and by the Химки leaderboard, which hand every approved user an `avatar_url` *and* a `vk_url` — the latter a permanent, globally-resolvable handle on the real person, strictly stronger than anything the yard adds. And the audience is an **allowlist the owner approved by hand**: "a stable handle on every other player" is a real property, but these players already know each other by name.

_Consequence — why it is fetched by id rather than broadcast, which is the part that was got wrong first._ The obvious implementation put the URL on the `Peer` struct, and it was wrong twice over. It is **expensive**: the roster is idempotent full state at 5 Hz, so a couple of hundred characters that never change would be re-sent for every player, on every tick, to every viewer — about a megabit a second of egress at ten people in a yard, growing with players times viewers, on an audience holding phones on mobile data. And it is **durable**, which the frame is not: a VK URL comes from Postgres and survives a restart, while the pseudonym beside it dies with the process — so two frames from either side of a deploy would have been linkable by it, quietly undoing the one property the pseudonym exists to have. Asking for the picture by the handle already in the frame costs **nothing** on the wire, is cached by the browser after the first ask, and leaves the frame free of personal data exactly as it was before. `AvatarFor` scans the display cache rather than keeping a reverse map, because a second map is a second thing to keep in step and a stale entry there would serve one person's face for another.

_What it still costs, and it is worth naming._ The route redirects to VK rather than streaming the bytes, so a viewer's browser does contact VK's CDN once per face, and VK can observe who is co-present. That is not a new exposure — the wishlist, the comments and the leaderboard already load the same pictures straight from VK for the same audience — but it is the one thing proxying would fix, and proxying for the yard alone would leave two ways to fetch one face. If it is ever worth removing, it is worth removing for all four at once. `img-src … https:` in the CSP is likewise load-bearing rather than merely permissive, because the stored URL is exactly what VK returned and is validated nowhere.

_How stale a face gets, and why it cannot be fixed here._ Three things cache it: the browser for five minutes, the display cache until the next hello, and `accounts.avatar_url_enc` — written by `UpsertOnLogin` **at login and nowhere else**. The third dominates, so a player who changes their VK picture keeps the old one here until they sign in again. Polling VK is not available as a fix: [ADR-006](./ADR-006-vk-tokens-are-discarded-after-the-profile.md) discards the token once the profile is read, and there is nothing left to ask with. The failure is benign — VK drops the old picture, the CDN 404s, and the client draws the catalogue art — and the wishlist and leaderboard have always been stale the same way.

_The tick never fetches it._ An avatar is read once per hello and held in the display cache, for exactly the reason [ADR-041](./ADR-041-the-broadcast-tick-renders-from-a-cache-and.md) gives about names and skins: the 5 Hz broadcast reads nothing but memory, and an account lookup on it would be a query per player per frame to re-fetch a URL that changes roughly never. The cache carries it across a pet write rather than rebuilding it, because a verb rewrites the pet and knows nothing about the person — without that, pressing a button would strip your own face off the plane until your next reload.

_Found while fixing the identity half:_ the connection-cap rejection never actually delivered its `bye`. `Register` runs after the 101, and the refusal path called `Conn.Close`, which only queues onto a channel that the write pump drains — and `Serve`, which starts that pump, is never reached for a refused connection. So the frame explaining "too many connections" was written to nobody and the socket was dropped bare. `Conn.Refuse` now writes it on the calling goroutine, which is safe precisely because no pump exists yet to race it.
