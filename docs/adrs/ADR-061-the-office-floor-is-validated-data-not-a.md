---

The office in «СИМУЛЯТОР ФИНТЕХА» used to be eight desks written out in `content.go`, and the whole game leaned on it: "this game's simplification against «ВАНЯДУМ» is that the level never changes" appears in the package doc, in the migration header, in the runbook and in three records. It changes now. The floor is a **`Layout`** — a list of solids and a list of windows — held in `game_fintech_layouts`, read once at boot, validated by one predicate before anything is allowed to stand on it, and identified by a hash of its own geometry.

_Why data rather than a seed, which is what the sibling game does._ [ADR-050](./ADR-050-the-level-is-generated-on-the-server-and-sent.md) stores eight bytes and regenerates a заброшка exactly, and that is right there because **every** заброшка comes out of the generator. It cannot be right here, because the point of this work is that a floor can also be **drawn by hand**: an office somebody dragged into shape has no seed, and there is no function from a seed to it. A seed column would therefore be true of some rows and a lie on others, which is the worst shape a column can have — a field whose meaning depends on which row you are looking at, silently. So the geometry itself is the stored thing, and the generator becomes one of several ways to produce a value rather than the only definition of what a floor is. It also removes the trap ADR-050 names, from the other end: there is no second implementation of a generator anywhere, because there is no generation on the read path at all.

_One `jsonb` body, not a row per solid._ The layout is read whole, written whole, and never queried by its parts — nothing selects the desks in the top half, nothing joins against a flowerpot. What a row set would add is an **ordering column**, and it would have to be maintained forever, because the **order of the solids is part of the collision contract**: `Step` pushes a body out of each rectangle once, in layout order, and so does the TypeScript port. The same rectangles in a different order are a different office to anybody standing between two of them. A jsonb body preserves that order for free and is the same value that is served. This is [ADR-039](./ADR-039-game-content-is-a-go-catalogue-and-the-schema.md)'s **named trigger firing**, not an exception to it — that record said the first kind needing a persisted, kind-specific, non-derivable value would earn its column or its side table *then*, with the concrete case in hand, and a floor somebody drew is exactly that case. Game *content* is still a Go catalogue; what is stored here is one authored **instance**.

_The id is a content hash, and it is not stored._ `Layout.ID` is the first sixteen hex digits of a SHA-256 over the canonical JSON of the geometry, computed on load. A row id would answer "who last wrote a row"; a content hash answers "is my cached geometry still the office", which is the question a browser actually has. Two identical floors have the same id on every process and after every deploy, so a restart that changed nothing invalidates nothing — and because the hash is recomputed rather than read, a row **cannot** carry an id that disagrees with its own body. That is the same contract `world_id` carries in [ADR-060](./ADR-060-there-is-one-zabroshka-nothing-ends-and-a-run.md), arrived at for the same reason and paid for the same way: it rides the **catalogue** and the HTTP shift response, never a frame. `POST /shifts` and `GET /shifts/current` answer with `office_id`, sixteen bytes once per shift, and the service reads it **inside the same critical section as the join** — between the join and a second lookup the floor could have been replaced, and telling a client the id of a floor its shift was not joined on is precisely the stranding the id exists to prevent.

_Validity is one predicate with three callers, and that is the decision rather than a convenience._ `ValidateLayout` answers what is wrong with a floor, in stable snake_case codes with the index of the object at fault. The generator will use it to accept a candidate, the admin save path will use it to accept a drawing, and the tests use it on the floor this game shipped with. A hand-made office is held to **exactly** the rules a generated one is, because the alternative — a generator that guarantees its output by construction and an editor that checks a subset by hand — is two definitions of "playable" that drift the first time one of them is retuned, and the drift shows up as a player wedged in a corner rather than as a failing test. Codes rather than prose for two reasons: an editor has to point at the offending object, and this project never returns an error's text to a client. The Russian for each code is written once, in the browser, where the rest of this game's Russian lives.

_`ResolverFloor` is the price of keeping the resolver single-pass, and it is worth naming what the alternative costs._ `Step` clamps a body to the floor and then pushes it out of each rectangle once, in order. That is only correct while nothing is close to anything else: two solids nearer than two body widths can hand a body out of one and into the next and leave it there, and a solid nearer than that to a wall can push a body clean out of the room, because the floor clamp has already run and nothing puts it back. The alternative is an **iterative** resolver — loop until nothing overlaps — and that function does not exist once. It exists twice, in Go and in TypeScript, has to converge identically in both, and is pinned by **232 kB of golden vectors** ([ADR-052](./ADR-052-the-netcode-is-built-multiplayer-complete.md)) that would all have to be regenerated. So the bound is bought with a **layout rule** instead: `Clearance` is the widest body on the floor (`BossRadius`, 0.40 m — a test pins that it is still the maximum of the two), `ResolverFloor` is twice it, and no legal floor comes near it. This is the load-bearing asymmetry of the whole design: **the geometry is constrained so the simulation does not have to be.**

_`MinGap` is the playability number and it is far above that floor, which is deliberate._ Every solid keeps 1.5 m from every other solid **and from every wall** — nearly twice `ResolverFloor`, so correctness is never the binding constraint and the number can be retuned as a feel. It leaves 0.7 m of daylight once the widest body is subtracted: enough to steer through at a walk, tight enough that a floor can be dense. It was 2.3 m for one afternoon — the widest body plus the 1.5 m of daylight the old symmetric aisles were designed against — and that was measured rather than argued: a mean of **7** solids per floor, **no greenery at all on 46 %** of them, and **no legal position left to place a single 1 × 1 object on 59 %** of them, which is an editor that cannot place anything and an office with nothing in it. The two numbers are separate because they answer separate questions, and conflating them is how a feel change becomes a correctness bug.

_Separation is measured per axis, and the euclidean version is a defect rather than a refinement._ Two rectangles expanded by *r* are disjoint **if and only if** they are more than 2*r* apart along X **or** more than 2*r* apart along Y. A pair offset diagonally by (0.6, 0.6) is 0.85 m apart as the crow flies — comfortably past a 0.8 m euclidean test — and yet their expanded boxes overlap, which is exactly the state a single-pass resolver cannot survive. The office shipped with a euclidean check in `content_test.go`; it never bit, because the eight desks were five metres apart, and it would have bitten the first afternoon a generator was allowed to place anything. `sepAxis` is `max(gapX, gapY)`, and it is the one piece of arithmetic in this record that is easy to get subtly wrong and impossible to notice.

_And the floor has to be one place._ `ValidateLayout` flood-fills the navigation grid from the лысый's own spawn and refuses a floor whose free space is not a single connected region. Under the gap rule this is nearly impossible to violate — the narrowest legal passage is 1.5 m, three cells of the grid — so it is not what keeps the office playable day to day. It is there because it is the only check that would notice if the gap rule were ever relaxed or given an exception, and because a pocket the лысый cannot reach is the one defect in this game that is invisible until somebody has been standing in it for a minute. `navigate.go` exists because of exactly that failure, measured at ninety seconds; and a player he cannot reach is **immortal**, which puts a score on a seven-day leaderboard that outlives the office that produced it.

_The navigation grid had to stop being process-wide, and this is where the old design actually broke._ It was a package-level `sync.OnceValue` over the catalogue's constant desks — correct, cheap, and deliberately not a function of the argument `StepBoss` was handed, with a comment saying so. It is exactly wrong the moment the floor can change: a rebuilt office would go on pathing round the furniture of the office before it, which presents as the лысый walking into thin air and grinding against a desk that is not there. Rebuilding it per tick is not the answer either — 1408 cells against a 20 Hz loop. So the grid moved into a **`Plan`**: a layout as the simulation uses it, the ordered collision list plus the grid, derived once when a layout is installed and immutable thereafter. An office swaps its whole plan for another rather than editing the one it holds, which makes "the floor changed" a single pointer write under one mutex instead of a half-updated world. The service holds the plan the **next** office will open on, because it outlives every office — an empty process still has to be able to tell a splash screen what the room looks like — and an office keeps its own pointer for its whole life, so a floor that changes never changes under a shift in progress.

_A solid's kind is a look, and it is kept out of the simulation by TYPE rather than by convention._ A `Solid` is a `Rect` plus a `Kind` — `desk`, `flower`, `tree` — so the browser can draw a ficus differently from a workstation, and **every solid collides identically**. The reason that has to be enforced structurally is that the collision code exists twice: the browser runs its own copy of `Step` for prediction, and the two must agree exactly. A rule of the form "remember not to branch on kind" survives until the first person who wants a plant you can walk through. So `Plan.Rects()` hands out `[]Rect`, `Step` takes `[]Rect`, the kind is not in the type at all by the time anything collides, and there is no path by which one could change what a body touches. A test asserts the plan never hands a kind out. Windows are the same argument taken further: a pane is a **span on a wall** — a wall, a distance along it, a length — with no thickness, no collision and no presence in the simulation, which is exactly why it cannot desynchronise anything.

_A missing floor is a state; a broken one is not._ `EnsureLayout` runs once, at boot, before the service is constructed. An empty table is what a fresh database looks like, so it installs `StartingLayout` — the eight desks this game shipped with, plus a ficus, a flowerpot and seven windows — and says so. A stored row that does **not** validate is a different matter: it is geometry the single-pass resolver has no answer for, so it is refused in favour of the starting floor and logged, rather than served. Failing to *write* the starting floor is not fatal either — the process stands up on the in-memory copy, because this table is one game's furniture and the landing page, the wishlist and three other games have nothing to do with it. The layout is a **parameter** to `NewService` rather than something it reads, because reading it is a database round trip and a constructor takes no context: the composition root does it once, which also means there is no state in which the service is running without a floor.

_What this deliberately did not do._ It did not make the floor per-shift — there is still exactly one office ([ADR-056](./ADR-056-the-office-is-one-process-wide-arena-not-one.md)) and now exactly one floor under it. It did not put geometry on a frame; `TestTheOfficeIsNeverOnAFrame` was widened from the snapshot to the ready and over frames precisely because a floor that changes makes "answer the change by sending the office" a live temptation for the first time. It did not add a seed column, a day column or a per-solid table. And it did not itself build the generator, the admin section, the rotation or the editor — those are the four iterations after it. Three of them have since landed on this model without moving any of it, which is the value of having shipped the model first: when they arrived there was nothing left to decide about what a floor **is**. The rotation did add one thing this record deliberately left open — a floor that is derived from a number rather than stored — and it is a *second producer of a value*, not a second definition of what a floor is; [ADR-062](./ADR-062-the-days-office-is-a-function-of-the-day.md) holds that reasoning. The editor is the one still outstanding.
